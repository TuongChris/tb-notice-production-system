MySQL 8.4 Reference Manual, "The DATE, DATETIME, and TIMESTAMP Types": the supported DATETIME range is
'1000-01-01 00:00:00' to '9999-12-31 23:59:59'; "With the fractional part included … the range for
DATETIME values is '1000-01-01 00:00:00.000000' to '9999-12-31 23:59:59.499999'".

## What the contract admits (ajv-formats "full" date-time)
Date part \d{4}-\d{2}-\d{2} (years 0000–9999, calendar-checked); separator T, t or ANY single
whitespace character; seconds with ANY number of fraction digits; offset Z/z, ±HH:MM, ±HHMM or ±HH;
a "leap-second" branch that accepts second 60 whenever the UTC time is 23:59 — and, through its
arithmetic, also hour-24 / minute-overflow forms with an offset (e.g. 2025-06-30T24:59:30+01:00).

## P3B before R7 (authority event effectiveAt): the rule judged and converted with V8's Date parser
storabilityProblem() accepted a value when new Date(value) was valid, had ≤ 3 fraction digits and a
UTC date 1000-01-01…9999-12-31; the write used new Date(value). V8 falls back to a legacy parser for
any separator other than T/t, and that parser reads 4-digit years 0000–0099 as 1950–2049:
  new Date('0050-06-30 10:00:00Z') → 1950-06-30T10:00:00.000Z   (100 of 100 years 0000–0099 shift,
  for space, TAB, LF, NO-BREAK SPACE and IDEOGRAPHIC SPACE separators; none with T or t)
so '0050-06-30 10:00:00Z' (wire-valid) passed the range check and would have been stored as 1950 —
a silent date change. The same rule also refused exactly storable values ('….123000Z', '…+05') and
accepted the last half-second of 9999 (…23:59:59.500–.999Z), outside MySQL's documented range.

## Root cause (one, shared)
Values were judged and converted by parsers that disagree with the wire oracle and with the column:
P3A had no storability check and passed the raw string through Prisma's DateTime parser and the
adapter's JS Date conversion (leap second → Invalid Date → '0NaN…' → 1292 → 500; microseconds cut
by JS Date; years outside MySQL's range stored or shifted on read); P3B's check relied on V8's
parser. Fix: one exact component parser of the contract grammar (infrastructure/write/storability.ts)
decides storability for both, and the exact Date it computes — never the request string — is written.
