AUD018-RED-01 — LOW (pre-existing since P2; classified per mission §39, NOT changed)
  `fieldAttributions[].scopeText` (≤ 3,000) and `.limitations` (≤ 5,000) of an Agency or LegalSubject are stored raw in
  AGENCY_CREATED/_UPDATED and LEGAL_SUBJECT_CREATED/_UPDATED: `REDACTED_FIELDS` names scopeText and limitations, but
  `auditValue` redacts only a top-level string and does not look inside the attribution array. It is directory
  attribution text — not a password, token, candidate or correspondence body, supported conclusion or rationale — and
  the contracted directory reads return the same text in full to the same signed-in users, so the audit read adds only
  its history. The audit read returns rows exactly as stored (no read-time redaction that would pretend storage is
  clean). A write-side change (redacting nested attribution text in future events) needs its own decision: backlog.

REV-FINAL-02 — LOW (pre-existing; outside the R14-AUD-016 scope, NOT changed)
  Capture accepts `askDispositions` on any gate (the contract allows them; the page offers them only for G6 of a reply).
  Readiness classifies disposition statuses only for G6 of an NMI_REPLY (R14-AUD-016); the integrity checks (a stored
  form, the prompt's parent, no ask twice, none on an INITIAL candidate) apply to every gate. A G1–G5 review recorded

REV-FINAL-03 — LOW (performance; local scale)
  listAuditEvents without filters, or with q, orders the whole audit_events table by (created_at DESC, id DESC); the only

OBS-FINAL-01 — observation (documented semantics)
  A guarded replay reads in one REPEATABLE READ snapshot and samples its evaluation instant right after those reads — the
  same semantics as the readiness GET. A record committed during the replay's own short read transaction is not seen by
  it (as with any consistent snapshot); the residual window is that transaction, no longer the claim and replay lookup
  before it. The first export keeps its SERIALIZABLE transaction under the case lock.

REV-FINAL-04 — LOW (policy question for the operator and the re-audit; NOT changed)
  The three resolved dispositions count without a structural presence check: `[{askId:'Q1', disposition:
  'ANSWERED_SUPPORTED', sourceIds: []}]` on a G6 PASS of a reply (everything else passing) is READY_FOR_SIGNER; so is an
  ANSWERED_WITH_LIMITATION with no limitation text and a NOT_APPLICABLE_WITH_REASON with no reason text
  (readiness-rules.ts ASK_DISPOSITION_CAUSE / evaluateGate; the contract's `sourceIds` has minItems 0 and the
  AskDisposition schema has no dedicated limitation or reason field — only `answerLocator` and `unresolvedRemainder`).
  Why not changed: mission §13/§15/§16 ask for the explicit enum plus the current source/scope checks, forbid treating
  source presence as proof and let the positive controls count; a presence rule would change capture or readiness
  semantics beyond the finding, and for the limitation and the reason it would first need a decision on which recorded
  field carries them (the contract defines none). The G6 PASS itself still needs 1–100 LINKED supports whose sources apply
  now, a visible rationale and scope text; every source a disposition does cite must apply now. The page states each
  resolved disposition's requirement in its option copy ("answered, with the cited sources supporting the answer",
  "answered within a limitation the reviewer records", "the ask does not apply, for the reason the reviewer records").

REV-FINAL-05 — LOW (test strength; documented)
  smoke:p4i's "replay judged at its own instant" check is end-to-end on the compiled API but not discriminating: the
  replay is sent after the temporal boundary has passed, so the pre-fix code (the executor's instant, itself after the
  boundary) would refuse it too. The compiled API has no seam to let time pass inside a replay; the discriminating proof
  is the DB tests A–D (READINESS_OBSERVER beforeReplayRead / afterReplayInput) and NC-FINAL-020-A/B. The record's §14
  says so.

REV-FINAL-06 — LOW (display only; beyond mission §30's "after any successful mutation"; backlog)
  The readiness shown is invalidated after a successful write. A write whose outcome the page does not learn (a network
  error or 5xx after the server committed) leaves the evaluation — or a prepared handoff — on screen until the next
  evaluation, or until a retry with the same idempotency key replays the success (which invalidates it). The server
  re-evaluates every export and replay, so nothing stale is released.

REV-FINAL-03 — LOW (performance; local scale; backlog) — also raised by the adversarial pass
  An unfiltered or q audit page orders the whole audit_events table (the only composite index,
  (entity_type, entity_id, created_at, id), serves the entity-filtered reads; q ORs six columns). An index on
  (created_at, id) needs a migration, which this mission does not authorize.
