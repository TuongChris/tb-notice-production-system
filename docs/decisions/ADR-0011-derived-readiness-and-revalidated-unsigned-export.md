## Context

- The frozen algorithm (INVARIANTS §2) derives readiness on every read and again on **every** unsigned export and export replay. It ends with UNVALIDATED, BLOCKED, REVIEW_REQUIRED, STALE_REVALIDATION_REQUIRED, READY_FOR_SIGNER or SUPERSEDED, with reason codes; G7 always stays HUMAN_PENDING and `externalAction` PROHIBITED.
- P4G records ValidationRuns bound to an exact artifact, digest and ruleset; P4H records CandidateAssessments bound to the epoch E of ADR-0008 with exact support rows, and provides the pure epoch and head helpers (`assessment-rules.ts`). D-6 (a disposition of technical REVIEW_REQUIRED issues) stays deferred.
- The `Readiness` wire object reports one `artifactSha256`, one `dependencyDigest` (required, 64 hex), one `rulesetVersion`, a nullable `validationRunId`/`technicalResult`, exactly six `GateSummary` rows and `reasonCodes`. `UnsignedExport` carries the candidate's exact subject, envelope and body with `signatureState` HUMAN_PENDING, `sendPerformed` false, the readiness evaluated for it and `exportedAt`.

## Decision

1. **One current epoch, derived by the server.** `E = (candidateId, artifactSha256, dependencyDigest, rulesetVersion)` (ADR-0008 Decision 3): the path's candidate, its stored artifact hash, the current digest of **exactly its prompt snapshot's scope** (the P4G/P4H path: `validationScope` → `readContextRows` → `assembleContext`, `TB-PRODUCTION-CONTEXT-DIGEST-v2` unchanged — no second context engine, no latest, default or replacement selection, parent or prior), and the ruleset the server runs now (`TB-TECHNICAL-RULESET-v3`). A client never supplies E. Every counted input binds exactly E: the counted run and every counted gate assessment — nothing is mixed across epochs.
2. **A scope that cannot be read has no epoch.** When a binding the prompt named has been corrected since, the reader refuses (`BINDING_ALREADY_SUPERSEDED`): no readiness is derived — GET is 409 `BINDING_ALREADY_SUPERSEDED` (a new prompt and candidate are needed) and an export is 412 `CONTEXT_CHANGED`. No digest is invented or substituted. This is the one case where a superseded candidate is not reported as SUPERSEDED: without a readable scope there is no truthful `dependencyDigest` for the Readiness object.
3. **Status precedence (strongest first; a nicer status never hides a stronger reason).** The order follows the frozen algorithm's steps: step 1, then the step-3 rejections of the scope and the step-9 artifact rules (properties no revalidation can change), then step 4 (the run), then the stronger findings of the current epoch before staleness of the reviews (mission §16), then everything that needs a review.

   | Tier | Status | Conditions (reason codes) |
   |---|---|---|
   | 1 | SUPERSEDED | `CANDIDATE_SUPERSEDED` — no newer candidate is chosen (INVARIANTS §2 step 1) |
   | 2 | BLOCKED | the scope or artifact is rejected: `CASE_ARCHIVED`, `PREPARATION_MODE` (a PREPARATION prompt's candidate is never production-ready), `CONTEXT_INPUT_MISSING` (the DRAFTING gate refuses the current context), `CONTEXT_TOO_LARGE`, `ARTIFACT_INTEGRITY_FAILED` (the stored text no longer hashes to its recorded hashes), `SIGNATURE_SLOT_INVALID` |
   | 3 | UNVALIDATED | `VALIDATION_MISSING` — the candidate has no validation run at all |
   | 4 | STALE_REVALIDATION_REQUIRED | `VALIDATION_STALE` — runs exist, none of exactly E |
   | 5 | BLOCKED | at E: `VALIDATION_BLOCKED`, `VALIDATION_ERROR` (the latest run of E is ERROR), a `TECHNICAL_RUN_CONFLICT` among whose completed runs one is BLOCKED (or whose latest run is ERROR), a gate BLOCKED (`G<n>_BLOCKED`, including `ASSESSMENT_INTEGRITY_FAILED`) |
   | 6 | STALE_REVALIDATION_REQUIRED | a gate's reviews are stale: `ASSESSMENT_STALE` (history but no current head of E), `G1_TEMPORAL_REVIEW_STALE` |
   | 7 | REVIEW_REQUIRED | `VALIDATION_REVIEW_REQUIRED` (with `PLAN_SOURCE_NOT_IN_CONTEXT` when that rule reported), `VALIDATION_COVERAGE_INCOMPLETE`, any other `TECHNICAL_RUN_CONFLICT`, `CONTEXT_CONFLICTS`, `CONTEXT_MISSING_ITEMS`, `AUTHORITY_EFFECTIVE_DATE_NOT_REACHED`, `TEMPORAL_BOUNDARY_AMBIGUOUS`, gates HOLD, MISSING, CONFLICT or never assessed (`G<n>_HOLD`, `G<n>_MISSING`, `G<n>_CONFLICT`, `G<n>_UNASSESSED`) — G6 held by an unresolved ask among them (`G6_ASK_REQUIRES_DOCUMENT`, `G6_ASK_MISSING_FACT`, `G6_ASK_LEGAL_REVIEW_REQUIRED`) |
   | 8 | READY_FOR_SIGNER | none of the above |

   Deviation from the mission's recommended order, taken from the frozen algorithm: the step-3 rejections (tier 2) come before UNVALIDATED — a never-validated candidate of an archived case or of a PREPARATION prompt is BLOCKED, since no validation can make it ready.
4. **The technical run (INVARIANTS §2 step 4; mission §9–§12; revised for R14-AUD-015).** Only runs of exactly E count (a v1 or v2 run never does; history stays readable), the latest recorded first, `(createdAt DESC, id DESC)`. No run at all → UNVALIDATED; runs but none of E → STALE_REVALIDATION_REQUIRED. A run of E **completed** when its result is not ERROR and its coverage manifest shows every rule the current ruleset requires executed and none not executed. A run that did not complete — ERROR (a rule failed while running) or a rule not executed — is a diagnostic: it produced no finding about the candidate (the ruleset: nothing follows from an execution failure).
   - **Historical diagnostics stay history.** An earlier run that did not complete stays readable, byte-identical history and is not compared with anything: a later completed run recovers from a transient diagnostic failure (ERROR → a completed TECHNICAL_PASS counts the PASS).
   - **A newer diagnostic is relied on as what it is.** When the latest run of E did not complete, it is the run that counts (`validationRunId`) and it is never READY: ERROR → BLOCKED with `VALIDATION_ERROR` (and `VALIDATION_COVERAGE_INCOMPLETE`: its failing rule is not executed); a run with a rule not executed → `VALIDATION_COVERAGE_INCOMPLETE`. No older PASS is relied on until another completed run is recorded.
   - **Completed runs that disagree fail closed.** Completed runs of E are compared by their material outcome — result, coverage manifest and the deterministic issues as (rule id, check kind, severity, field path); issue messages and details are not compared (details may name an owner the digest does not fingerprint, ADR-0008 Decision 4), and heuristic signals only through the result they produced (a heuristic is a signal for a person, never a finding). Completed runs that disagree → `TECHNICAL_RUN_CONFLICT`: no run counts (`validationRunId` and `technicalResult` null), each disagreeing completed run's result code is listed (and the latest run's own codes when it did not complete), status BLOCKED when one of them is BLOCKED (or the latest run is ERROR), else REVIEW_REQUIRED. Never "the latest PASS wins": a newer PASS does not resolve a conflict with a completed BLOCKED or REVIEW_REQUIRED run, and a diagnostic run neither resolves nor hides it.
   - **The counted run** — the latest run of E, when no conflict exists (a completed one is then equivalent to every other completed run of E) — maps: BLOCKED → BLOCKED; REVIEW_REQUIRED → REVIEW_REQUIRED; TECHNICAL_PASS → the gates. A TECHNICAL_PASS counts only with `notExecutedRuleIds` empty and every rule the current ruleset requires executed (`VALIDATION_COVERAGE_INCOMPLETE` otherwise); a stored BLOCKER or REVIEW_REQUIRED issue of the counted run is never overlooked whatever its recorded result (an ERROR run's diagnostic issues are represented by `VALIDATION_ERROR`).

   *As accepted at P4I (superseded by the revision above):* Only completed runs of exactly E count (a v1 or v2 run never does; history stays readable). No run at all → UNVALIDATED; runs but none of E → STALE_REVALIDATION_REQUIRED. Several runs of E are compared by their material outcome — result, coverage manifest and the deterministic issues as (rule id, check kind, severity, field path); issue messages and details are not compared (details may name an owner the digest does not fingerprint, ADR-0008 Decision 4), and heuristic signals only through the result they produced (a heuristic is a signal for a person, never a finding). Equivalent runs → the most recently recorded one counts, `(createdAt DESC, id DESC)`, reported as `validationRunId`. Runs that disagree → `TECHNICAL_RUN_CONFLICT`, no run counts (`validationRunId` and `technicalResult` null), status BLOCKED when any of them is BLOCKED or ERROR, else REVIEW_REQUIRED. The counted run maps: BLOCKED → BLOCKED; ERROR → BLOCKED with `VALIDATION_ERROR` (and `VALIDATION_COVERAGE_INCOMPLETE`: its failing rule is not executed); REVIEW_REQUIRED → REVIEW_REQUIRED; TECHNICAL_PASS → the gates. A TECHNICAL_PASS counts only with `notExecutedRuleIds` empty and every rule the current ruleset requires executed (`VALIDATION_COVERAGE_INCOMPLETE` otherwise); a stored BLOCKER or REVIEW_REQUIRED issue of the counted run is never overlooked whatever its recorded result. *(Under that wording every run of E was compared, a diagnostic ERROR run included, so one ERROR run and a later TECHNICAL_PASS of the same epoch conflicted and the epoch stayed BLOCKED until it changed — OBS-P4I-01, confirmed by the final audit as R14-AUD-015.)*
5. **No waiver (D-6 stays deferred).** READY_FOR_SIGNER requires a counted TECHNICAL_PASS with full coverage. No assessment, disposition, override, rebinding or re-draft turns REVIEW_REQUIRED into a pass. `PLAN.SOURCE_IN_CONTEXT` stays non-waivable (ADR-0008 Decision 2): it is reported as `PLAN_SOURCE_NOT_IN_CONTEXT` and no G6 assessment clears it. Version-only prompt drift stays REVIEW_REQUIRED: the baseline needs a new prompt and candidate.
6. **Gate heads (INVARIANTS §2 steps 5–6; mission §14–§18).** Per gate, the heads of the candidate's supersession chains (`assessmentHeads`) whose epoch is exactly E (`currentHeads`). None → UNASSESSED (`GATE_UNASSESSED`; `ASSESSMENT_STALE` when the gate has assessments of other epochs or only superseded ones). Two or more → CONFLICT (`GATE_CONFLICT`, `GATE_HEADS_UNRECONCILED`, no `assessmentId`) — never the latest or a convenient PASS; no majority, score or weighting. One head: HOLD → HOLD, BLOCKED → BLOCKED, MISSING → MISSING, CONFLICT → CONFLICT (`GATE_<result>`); PASS with RECORDED_NOT_ADOPTED → HOLD (`SCOPE_NOT_CONFIRMED`); PASS with SCOPE_CONFIRMED_FOR_CANDIDATE → PASS only if item 7 holds. An assessment of another candidate never counts, whatever its artifact. Stored rows never change.
7. **What a PASS head needs to count.** A performer label, rationale and scope text with visible text (`ASSESSMENT_RECORD_INCOMPLETE` → HOLD); a provenance other than MISSING or CONFLICT, which contradict a PASS (`ASSESSMENT_PROVENANCE_UNSUPPORTED` → HOLD); and intact supports (`ASSESSMENT_INTEGRITY_FAILED` → BLOCKED): 1–100 AssessmentSource rows, each naming a CaseSource of the candidate's case that is LINKED now and whose source the current context lists as applying to the case. Under the epoch these hold for every capture P4H accepted (a later link or applicability change moves the digest); they are integrity checks that keep a corrupt or inconsistent row from counting, never a re-reading of history.
8. **G6 and NMI asks (INVARIANTS §2 step 7; mission §20–§21; PFC §6; revised for R14-AUD-016).** G6 is a recorded G6 assessment of exactly E, independent of the technical run — neither implies the other. The system records no structured list of an NMI's asks: they exist only as a G6 reviewer's ask dispositions. For an NMI_REPLY candidate a counted G6 PASS therefore needs:
   - **at least one ask disposition** (`G6_ASK_DISPOSITIONS_MISSING` → HOLD);
   - **each in its stored form, of exactly the prompt's parent binding, each ask once**: an entry with its ask id, parent binding, a contracted disposition and its source list; a malformed entry, a disposition outside the contracted six, another parent or an ask (parent binding, ask id) recorded twice → `ASSESSMENT_INTEGRITY_FAILED` (BLOCKED; capture refuses all of them, so only a corrupt row has one);
   - **every disposition resolved.** A disposition is the explicit recorded status of its ask, never mere presence. `ANSWERED_SUPPORTED`, `ANSWERED_WITH_LIMITATION` and `NOT_APPLICABLE_WITH_REASON` are resolved — a limited answer or a reasoned non-applicability is the reviewer's attributable conclusion. `REQUIRES_DOCUMENT` (`G6_ASK_REQUIRES_DOCUMENT`: a requested document is still needed), `MISSING_FACT` (`G6_ASK_MISSING_FACT`: a material fact is still missing) and `LEGAL_REVIEW_REQUIRED` (`G6_ASK_LEGAL_REVIEW_REQUIRED`: a legal review is outstanding) are unresolved by their own recorded status and hold G6 (HOLD, REVIEW_REQUIRED) — alone or beside answered asks; answered asks and five PASS gates never compensate. PFC §6: longer prose and removal of inconvenient wording do not cure an outstanding material document/fact requirement;
   - **every source a disposition cites existing and applying to the case now** (`G6_ASK_SOURCE_NOT_APPLICABLE` → HOLD; these sources can lie outside the closure, so the digest does not bind them). The source and scope rules of capture (an ask's cited sources must apply to the case, `assertSourcesUsable`; the supports are LINKED links of this case) stay unchanged.

   **No text is read.** The question, answer locator, unresolved remainder, limitations and rationale never change a disposition's classification: no keyword rule and no legal inference from text. No disposition is fabricated and a missing ask is never NOT_APPLICABLE. **Ask completeness is the reviewer's record:** whether the dispositions cover every material ask of the parent message cannot be decided by software — the asks exist only as captured correspondence text, and no structured record of them exists — so the system enforces what it can (at least one disposition, exactly the parent, no ask twice, contracted values only, sources applying now) and leaves completeness to the G6 reviewer's attributable record (`MATERIAL_SEMANTIC_AMBIGUITY`, recorded, never inferred). **Recovery is explicit:** a stored G6 PASS recording an unresolved ask stays unchanged and readable; only an explicit, sourced successor recording the asks resolved becomes the one head that can count. An INITIAL candidate carries no dispositions (capture refuses them; any stored one is an integrity failure) and no reply rule is imposed on it.

   *As accepted at P4I (superseded by the revision above):* For an NMI_REPLY candidate a counted G6 PASS therefore needs at least one ask disposition (`G6_ASK_DISPOSITIONS_MISSING` → HOLD), each naming exactly the prompt's parent binding (else `ASSESSMENT_INTEGRITY_FAILED`), none `LEGAL_REVIEW_REQUIRED` (`G6_ASK_LEGAL_REVIEW_REQUIRED` → HOLD: the disposition itself states that a review is outstanding), and every source a disposition cites existing and applying to the case now (`G6_ASK_SOURCE_NOT_APPLICABLE` → HOLD; these sources can lie outside the closure, so the digest does not bind them). No disposition is fabricated and a missing ask is never NOT_APPLICABLE. An INITIAL candidate carries no dispositions (capture refuses them; any stored one is an integrity failure) and no reply rule is imposed on it. *(Under that wording REQUIRES_DOCUMENT and MISSING_FACT did not hold G6, so a reply whose review recorded a document or fact still needed could be READY_FOR_SIGNER and exported — OBS-P4I-02, confirmed by the final audit as R14-AUD-016.)*
9. **Temporal review freshness (INVARIANTS §2 step 8; mission §22–§26).** Software checks only whether the counted G1 review predates a captured temporal boundary; the G1 review stays the substantive decision. The boundaries are those of the context's authority rows: the pinned MandateVersions' and MandateCoverages' `effectiveOn` and `expiresOn`, the selected signer's CoverageSigner rows' `effectiveOn` and `endsOn`, and each AuthorityEvent without a successor in the chain (a corrected event is replaced by its correction) at its `effectiveAt`, else its `effectiveOn`. No meaning of an event type is interpreted, a missing expiry stays UNKNOWN (never perpetual), `validityModel` alone decides nothing, and **time alone never stales anything**: there is no age rule.
   - Instants compare exactly: a boundary `e` with `assessedAt < e ≤ now` → `G1_TEMPORAL_REVIEW_STALE` (G1 UNASSESSED, tier 6).
   - Dates are civil dates in no known timezone: date `D` is taken as the interval in which it is `D` somewhere on earth (UTC−12:00 … UTC+14:00), from `(D−1)T10:00:00.000Z` inclusive to `(D+1)T12:00:00.000Z` exclusive. An instant before it is before `D` everywhere, one at or after its end after `D` everywhere, one inside it possibly on `D`. For the counted G1 review at `a`: `a` after the interval → the review is post-boundary; `a` inside it → `TEMPORAL_BOUNDARY_AMBIGUOUS` (G1 HOLD, REVIEW_REQUIRED); `a` before it → stale when `now` is after the interval, ambiguous when `now` is inside it, fresh while the boundary lies ahead. No midnight or timezone is invented.
   - `assessedAt` null is never replaced by `createdAt`: with a boundary reached (possibly or surely) the review cannot be placed → `G1_REVIEW_TIME_UNKNOWN` (G1 HOLD). An `assessedAt` after the evaluation instant is treated the same way: no actual review lies in the future.
   - A selected version, coverage or coverage signer whose `effectiveOn` lies ahead → `AUTHORITY_EFFECTIVE_DATE_NOT_REACHED`; one on its effective date → `TEMPORAL_BOUNDARY_AMBIGUOUS` (both REVIEW_REQUIRED; no legal invalidity is stated).
10. **Signature slot (INVARIANTS §2 step 9).** `signatureState` HUMAN_PENDING and the exact pending slot exactly once in the body and never in the subject — the same token and counting as the rule `SIGNATURE.PENDING_SLOT_ONCE` (`PENDING_SIGNATURE`, `exactOccurrences`); otherwise `SIGNATURE_SLOT_INVALID`. A signer's name elsewhere is not a signature. The artifact is recomputed with `TB-CANDIDATE-ARTIFACT-v1` and the body with `exactTextSha256` (`ARTIFACT_INTEGRITY_FAILED` otherwise).
11. **READY_FOR_SIGNER** only when nothing above applies. It means "ready for authorized human signer review": the candidate stays unsigned and unsent; `signatureState` HUMAN_PENDING and `externalAction` PROHIBITED are constants.
12. **Reason codes** are stable strings in a pinned order (`READINESS_REASON_ORDER`, `GATE_REASON_ORDER` in `modules/readiness/readiness-rules.ts`; a unit test pins both). A gate's list is `GATE_<STATUS>` followed by the gate's own causes (`SCOPE_NOT_CONFIRMED`, `G1_TEMPORAL_REVIEW_STALE`, …) and is empty exactly when the gate is PASS; the readiness list names each non-PASS gate as `G<n>_<STATUS>` plus the same causes, after the candidate-, context- and run-level codes. READY_FOR_SIGNER holds exactly when the readiness list is empty. No code carries record content.
13. **Readiness is read-only and never stored.** GET is one REPEATABLE READ snapshot (plain reads; `evaluatedAt` = the evaluation instant) and writes nothing — no audit event, idempotency record, row version, context revision or other change beyond the session activity of P1. There is no readiness table, column, flag, cache, `approvedAt` or approval state; no migration.
14. **The unsigned export re-evaluates readiness in its write.** Idempotency-Key, no If-Match; one short SERIALIZABLE transaction through the WriteExecutor (bounded retries, at most 3): the candidate (404) → its CaseRecord locked FOR UPDATE (an archived case is not refused here: its readiness is BLOCKED with `CASE_ARCHIVED`) → the candidate share-locked → the same readiness reader and rules at the current instant → the refusals, in this order, each against the readiness just evaluated and never substituted:
    1. `expectedArtifactSha256` ≠ its artifact → 412 `ARTIFACT_CHANGED` {field};
    2. `expectedDependencyDigest` ≠ its digest → 412 `CONTEXT_CHANGED` {field};
    3. not READY_FOR_SIGNER → 409 `CANDIDATE_NOT_READY` {status, reasonCodes};
    4. `validationRunId` ≠ its counted run → 412 `VALIDATION_RUN_CHANGED` {field}.

    A request whose artifact or digest is not the current one rests on a read that predates a change, and "read again" is the precise answer; only against the current artifact and digest is "not ready" meaningful, with the status and reasons of now; the run is compared last, since a status other than READY_FOR_SIGNER may count no run. (Archiving a case moves its digest, so an export against a read from before the archive is 412 `CONTEXT_CHANGED`, and against a fresh read 409 `CANDIDATE_NOT_READY` BLOCKED `CASE_ARCHIVED`.) Then one redacted audit event `EXPORT_UNSIGNED` → the response. Lock order CaseRecord → NoticeCandidate, then the reads of the readiness (P4H's order). Nothing external happens in the transaction or its retries.
15. **Exact bytes, nothing added.** The response carries the candidate's stored `subject`, envelope, `bodyText`, `bodySha256` and `artifactSha256` exactly — no trimming, normalization, newline rewrite, signer name or signature — with `signatureState` HUMAN_PENDING, `sendPerformed` false, the readiness evaluated for this export and `exportedAt` = that evaluation instant. No attachment bytes, MIME, ACTUALLY_ATTACHED, AS_SENT, SENT or SIGNED state or record exists; the document plan stays a plan.
16. **Export audit.** `EXPORT_UNSIGNED` (never SIGNED, SENT, SUBMITTED or NOTICE_SENT) records the candidate, case, artifact and body SHA-256, digest, ruleset, validation run, the readiness status, the six gates' assessment ids, the format, HUMAN_PENDING, `sendPerformed` false, `externalAction` PROHIBITED and the instant — the subject and body only as their lengths. No export table, row or copy exists.
17. **An idempotent replay rechecks before it releases anything (INVARIANTS §5; API_CONTRACT §7).** The idempotency record keeps the response status, meta, the evaluated readiness and `exportedAt` — never the subject, envelope or body. A replay of the same key and body re-evaluates the current readiness in a consistent snapshot — at an instant sampled after that snapshot's reads, right before the evaluation, as a GET does, never the request's instant, which precedes the idempotency claim, the replay lookup and those reads (R14-AUD-020; the guarded-replay callback receives no instant) — and applies exactly the refusals above against the original request; only when it is still READY_FOR_SIGNER with the same artifact, digest and run does it return the historical response, rebuilt from the immutable candidate with the stored readiness and `exportedAt`. Otherwise it returns the present refusal and releases nothing. A replay writes nothing (no new audit event); the same key with another body is 409 `IDEMPOTENCY_CONFLICT`. This is a WriteExecutor option (`guardedReplay`), used only by this operation.
18. **No-store.** Every API response is `Cache-Control: no-store` (P1 middleware); the export also sets it explicitly. The page reads the readiness only when asked and keeps a readiness or a handoff only while it shows it — no browser storage, cache or reuse; a new evaluation clears a shown handoff. A successful write on the candidate page that can change the readiness — the candidate's supersession, a technical validation run, a G1–G6 review — drops the evaluation and any handoff shown at once, and a response to a readiness or export request started before that write is discarded, never shown (R14-AUD-019); nothing is inferred in their place, and only a new evaluation shows a readiness again. Reads start nothing of the kind.
19. **No G7.** No signature capture, signer confirmation, personal adoption, send, email, SMTP, YouTube submission, Drive write, uploader contact, platform response or AS_SENT creation exists, and no button for them. G7 stays human and outside the application.

## Consequences

- Readiness can only be as current as the captured records. A source or authority change that was never captured cannot be detected; the page says so.
- Under the baseline a candidate reaches READY_FOR_SIGNER only when its prompt's context is the current context, its current run is a full TECHNICAL_PASS and six confirmed PASS reviews of that same epoch exist; any later context change needs new runs and reviews (and, for a changed context after the prompt, a new prompt and candidate, ADR-0008 W-2).
- A G1 review needs its actual review time once the selected authority carries a reached date: a missing time is never guessed.
- Since the revision (R14-AUD-015): a transient execution failure no longer blocks its epoch — re-running the validation of the same epoch recovers once a run completes; a newer ERROR or incomplete run still stops READY until another run completes; completed runs that disagree stay a conflict until the epoch changes.
- Since the revision (R14-AUD-016): a reply whose G6 review records a document still needed, a fact still missing or a legal review outstanding is never READY_FOR_SIGNER and is never exported; the stored review stays as recorded, and an explicit successor review recording the asks resolved (with its sources) is the only way on. Whether the recorded dispositions cover every material ask stays the reviewer's attributable responsibility.
- **Known limitation (backlog):** two supersession chains of one gate at the same epoch cannot be merged — a successor supersedes exactly one predecessor (D-2) — so the gate stays CONFLICT (`GATE_HEADS_UNRECONCILED`) at that epoch. It clears only when the epoch changes (a candidate revision, or a recorded change that moves the digest, followed by a new run and new reviews). A reconciliation workflow (one successor for several heads) needs its own ADR; nothing picks a head meanwhile.
- `TB-TECHNICAL-RULESET-v3`, `TB-PRODUCTION-CONTEXT-DIGEST-v2`, `TB-PROMPT-TEMPLATE-v1`, `TB-CANDIDATE-ARTIFACT-v1` and `PFC-YT-EMAIL-v1.1` are unchanged: readiness is a downstream derivation, not a technical rule or a context semantic.
- New implementation codes in the free-string `code` field with contracted statuses: `VALIDATION_RUN_CHANGED` (412); the frozen stable codes `CANDIDATE_NOT_READY` (409), `ARTIFACT_CHANGED` and `CONTEXT_CHANGED` (412) are used; `BINDING_ALREADY_SUPERSEDED` (409) is reused.
- The same mission carries one bounded remediation outside readiness, recorded in the P4I verification record: a CaseFact write's `meta.affectedResources` names the CaseFact and the CaseRecord only (API_CONTRACT_v1 §6, "affected root versions"), so 100 supports stay within the contracted bound of 100 entries.

## Alternatives considered

- **A readiness table or a stored READY flag** — forbidden by the frozen model (no persisted READY_FOR_SIGNER), and it would go stale. Rejected.
- **Replaying a stored copy of the export** (the default idempotency path) — would release a body after its readiness is gone and keep a second copy of the draft in the database. Rejected for the guarded replay.
- **Choosing the latest PASS among several heads, or the most recent run when runs disagree** — forbidden (INVARIANTS §2 step 6). Rejected.
- **Interpreting a date in UTC or the server's timezone** — invents a timezone. Rejected for the interval convention of Decision 9.
- **A universal review age (30/60/90 days)** — forbidden (INVARIANTS §2 step 8, PFC §12). Rejected.
- **A G6 disposition that clears technical REVIEW_REQUIRED issues** — D-6 stays deferred; it needs its own ADR and contract release. Rejected here.
- **Comparing every run of the epoch, diagnostics included** (the wording accepted at P4I) — an ERROR run records no finding about the candidate, and the comparison made an epoch unrecoverable after one transient failure (R14-AUD-015). Rejected at the revision.
- **Letting the latest completed run decide when completed runs disagree** ("the latest PASS wins") — would hide a completed BLOCKED or REVIEW_REQUIRED outcome behind a convenient one. Rejected.
- **Relying on an older PASS when the latest run is a diagnostic** — the newest run of the epoch did not complete, so nothing established since then is known to pass. Rejected: the latest run counts, and it is never READY.
- **Holding G6 only for LEGAL_REVIEW_REQUIRED** (the wording accepted at P4I) — a document still needed or a fact still missing is, by its own recorded status, not a resolved ask (R14-AUD-016, PFC §6). Rejected at the revision.
- **Deciding an ask's resolution from its text** (keywords in the remainder, locator or question) — software would be drawing a legal conclusion from prose. Rejected: the recorded disposition is the ask's status.
- **Evaluating a replay at the request's instant** (the P4I implementation) — that instant precedes the claim, the replay lookup and the replay's reads, so a boundary passing meanwhile was judged as not yet passed (R14-AUD-020). Rejected.
